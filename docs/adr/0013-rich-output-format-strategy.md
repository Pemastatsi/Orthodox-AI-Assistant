# ADR 0013: Rich Output Format Strategy

Date: 2026-05-19
Status: Accepted

## Context

Phase 1 delivers closed-corpus Q&A with plain-text answers and a structured citation list. This is sufficient for private beta but insufficient for the target audience of seminary professors, clergy, and institutional publishers who need to produce lesson plans, parish bulletins, lecture slides, and canonical briefings.

Competing platforms (Claude Artifacts, NotebookLM) offer rich output formats but are general-purpose and not grounded in a closed corpus. The Orthodox AI Assistant can achieve parity on output richness while maintaining a decisive advantage: every artifact is provenance-backed — no generated document, graph, or audio file can contain an unverified claim. That guarantee, absent from all general-purpose competitors, is the product's core differentiator in an institutional theological setting.

This ADR defines the five-tier output model, establishes the closed-corpus provenance rule for all artifact types, and sets the boundaries for Phase 2 implementation.

## Decision

Introduce a Rich Output layer as a first-class Phase 2 capability alongside the existing Q&A pipeline. All output tiers share a common `Artifact` envelope, all carry mandatory citation provenance back to approved evidence chunks, and all are subject to the same closed-corpus rules established by ADR 0001.

## Output Tiers

### Tier 1 — Rich Text Foundation
Markdown rendering with tables, lists, and blockquotes; Mermaid inline diagrams; LaTeX theological notation; footnote-style citations. Delivered in the existing `<AnswerPanel>` via a new `richText` flag on the verified response.

### Tier 2 — Visual Artifacts
Interactive visualizations rendered in the browser via the `ArtifactRenderer` interface (see ADR 0014):
- **Patristic Lineage Graph** — doctrinal influence network (Person, Work, Concept, Council nodes; edge types: `cites`, `builds_on`, `contrasts_with`, `derives_from`, `translation_of`).
- **Council Decision Timeline** — interactive scrolling timeline of ecumenical and local councils with linked canons.
- **Citation Network Graph** — cross-father citation frequency network.
- **Dispute Map** — side-by-side comparative position visualization (Orthodox / Catholic / Protestant / heretical) with per-claim evidence anchors.
- **Manuscript Witness Tree** — textual transmission lineage from manuscript families through critical editions to modern translations.
- **Mind Map / Outline View** — hierarchical answer outline auto-derived from the verified response.

### Tier 3 — Generated Documents
Structured documents generated by A5-class composition, evidence-coverage-checked, exported via the `ExportProvider` interface (see ADR 0014):
- Study Packet (PDF + DOCX) — reading list, citations, discussion questions.
- Sermon / Homily Builder (DOCX) — Gospel pericope + patristic commentary blocks + outline.
- Slide Deck (PPTX + Reveal.js HTML) — lecture-ready slides.
- Catechism Lesson Plan (PDF + DOCX) — adult inquirer / catechumen module.
- Parish Bulletin Insert (PDF) — short-form layperson-grade explainer.
- Bishop Briefing (PDF + DOCX) — institutional decision-support document.
- Syllabus Bundle (PDF + DOCX) — full course outline for seminary use.
- Feast-Day Bundle (PDF) — liturgical occasion learning material.
- Parish FAQ Draft (DOCX) — community-facing Q&A.

High-stakes documents (Bishop Briefing, Syllabus Bundle, Catechism Lesson Plan) require the approval gate defined in ADR 0016 before export.

### Tier 4 — Audio Overview
Two-voice dialogue TTS synthesis via the `TTSProvider` interface:
- Generated from the verified response + key citations.
- SSML-tagged for theological proper nouns and Greek terms.
- Citation timestamps embedded as chapter markers.
- Pronunciation guide applied for patristic names, Greek/Slavic ecclesiastical terms.
- Metered separately as `audio_minutes_generated` (see ADR 0015).

### Tier 5 — Orthodox-Unique Multimedia
Specialized features with no competitor equivalent:
- **Bilingual Side-by-Side** — Greek + English with hover morphology (SBLGNT/Septuagint via the `MorphologyProvider` interface).
- **Liturgical Calendar Overlay** — query contextualized against today's feast/saint/readings.
- **Iconographic Reference Cards** — icons sourced from curated database via `IconographyProvider`; never AI-generated.
- **Byzantine Chant Integration** — linked traditional melodies when troparia/hymns are referenced, via `ChantProvider`.
- **Holy Land + Monastery Map** — geographical context (patriarchates, monastic houses, hagiographic sites) via `MapRenderer`.
- **Disputation Simulator** — evidence-gated exploration of Orthodox responses to common theological objections.

## Closed-Corpus Provenance Rule (extends ADR 0001)

Every artifact, regardless of type, must satisfy:

1. **Citation carry-through.** Every claim in a generated artifact maps to one or more `citationRefs` linking to approved `chunk_id` values in the evidence packet. The artifact schema enforces `citationRefs` as a required field.
2. **No supplementation.** Artifact generation agents may not introduce claims sourced from model training data, open-web content, or unapproved graph edges. The closed-corpus composition rules of A5 apply to all artifact-generation steps.
3. **Verifier pass.** Before any artifact is stored or delivered, A6-equivalent citation verification runs over its content. Graph artifacts verify node and edge sources; audio artifacts verify script claims; document artifacts verify all factual assertions.
4. **Suppression of candidate data.** Candidate (unreviewed) graph edges, unapproved corpus chunks, and admin-only sources are never rendered into user-visible artifacts, identically to the Q&A pipeline.

## Rules

1. Every artifact type has a corresponding JSON schema under `docs/schemas/`; schemas are required before implementation.
2. Every artifact is stored in the `artifacts` table with `tenantId`, artifact type, status, evidence-packet reference, and `citationRefs`.
3. Artifact generation is always triggered explicitly by the user or admin; the system never auto-generates artifacts without a request.
4. All artifact rendering is provider-abstracted per ADR 0014; no hard-coded library calls in business logic.
5. High-stakes artifact types defined in ADR 0016 require approval before export.
6. Audio minutes, document exports, and visual artifacts are metered per ADR 0015.
7. Safety classification (A1) runs on artifact-generation requests identically to Q&A requests; a `block_with_redirect` handling exits the artifact pipeline before any generation.
8. Artifacts are cache-eligible; cache keys include tenant, artifact type, source evidence-packet version, render-route version, locale, and tenant branding version.
9. All artifact content is scoped to the requesting tenant; cross-tenant artifact data is forbidden.
10. The `IconographyProvider` and `ChantProvider` may only source material from the curated licensed set; AI-generated images and synthetic chant recordings are permanently prohibited.

## Tests

- Artifact schema validation: every artifact type schema has a JSON Schema Draft 2020-12 test vector.
- Citation carry-through: generate a stub artifact; assert every claim node in the artifact has at least one `citationRef` pointing to an approved chunk.
- Closed-corpus enforcement: attempt to generate an artifact with a claim sourced outside the evidence packet; assert generation fails with `insufficient_evidence`.
- Safety gate: send an artifact-generation request that triggers `block_with_redirect`; assert no artifact is created.
- Tenant isolation: attempt to render an artifact using chunks from a different tenant; assert the request is rejected.
- Approval gate: attempt to export a high-stakes artifact without approval; assert export fails with `pending_approval`.
- Cache hit: generate the same artifact twice with identical inputs; assert second call returns from cache without triggering a new generation.
- Provider swap: replace the default `GraphRenderer` route with a stub; assert the artifact pipeline continues to produce valid output.
